# 推给开发者以外的角色

日期：2026年10月22日  
状态：**想法，未定，不一定做。** 先存着，等日用一段时间、有真实卡点再回来看。

## 出发点

Folmi 真正的东西不是 Git 图形界面，而是一件和角色无关的事：**AI 改了我的文件，我一处一处决定留不留，每一步都退得回。** 推给别的角色，不是做另一个产品，而是两件事：找到「也在让 AI 改本地文件」的人；把只有开发者需要的那一层藏起来。

## 候选方向（按离现有能力由近到远）

| 方向 | 谁 | 现有能力能用多少 | 主要缺口 |
| --- | --- | --- | --- |
| 1. 写文档的人 | 技术写作、产品文档、知识库、写长文的人 | 阅读视图、渲染差异、大纲、文档历史、编辑辅助 | 不要求 Git；按段落收下；去掉 Git 词 |
| 2. 用 AI 改原型的产品、设计 | 用 Claude Code 改前端原型、样式、文案 | 说人话、钩子、按轮次看 | 看效果（前后截图 / 预览）而不是看差异；按意图分组；风险提示 |
| 3. 非开发类 agent 用户 | 用桌面 agent 整理文件夹、改表格、配置、翻译文件 | 很少 | 没有钩子、没有轮次；结构化差异（JSON / YAML 按键、CSV 按行） |
| 4. 团队审阅者 | tech lead 看同事和同事的 AI 的改动 | 大部分 | 和「不轮询服务器」冲突，先不考虑 |

都要先补的底层：不要求先有 Git；按角色的界面模式；「一处」按内容定（代码按块、Markdown 按段落、表格按行、配置按键）。

风险：入口从「钩子通知」变成「监听文件夹」，按轮次看这类强项变弱；只有 macOS；定位被稀释。**只选一个方向验证，不同时铺开。** 下面细化方向 1。

## 方向 1：写文档的人

### 他们是谁、怎么用 AI

- **docs-as-code 的写作者**：产品文档、API 文档、内部手册，本来就在 Git 仓库里，但自己不太懂 Git，靠开发同事帮忙提交。用 Claude Code / Codex 批量改术语、补章节、按新版本同步说明。
- **个人知识库**：Obsidian 之类的一个文件夹的 Markdown，没有 Git。让 AI 整理标签、拆合笔记、改链接、统一格式，一次动几十上百个文件。
- **写长文的人**：方案、报告、书稿、博客，一个或几个大文件。让 AI 润色、改结构、压字数，每轮改动分散在全文。

共同点：改动以 Markdown 为主；**在乎读起来怎样，不在乎行号**；AI 一次改很多处，自己既不想全看也不敢全收；出错的代价是「好好一段话被改坏了还没发现」。

### 现在用什么、哪里不顺

- AI 工具里直接看对话里的改动摘要：看不全，看完也没法一处处挑。
- Word 修订 / Google Docs 建议：能逐处接受，但 AI 改本地 Markdown 文件夹时用不上，跨文件更没有。
- Git 客户端 / VS Code 差异：按行比较源码，一个改了标点的长段落整段标红；分支、暂存这些词劝退。
- Obsidian 的文件恢复：只能整篇回到某个时间点，不能只要其中两处。

Folmi 能占住的一句话：**AI 改了你一整个文件夹的文档，在这里像看修订一样一处处收下或退回，随时退得回去。**

### 主循环（文档模式）

AI 改完 → 通知「这一轮改了 12 篇、47 处」→ 渲染后的修订视图逐处看（空格下一处，⏎ 收下，⌫ 退回，⌥⌘Z 撤销）→ 存一个版本（说明后台写好）→ 有远端才出现「同步」。

和现在的差别：看的永远是渲染后的文字；「一处」是一段而不是一个代码块；没有提交、推送这两个词。

### 要做的事

按依赖排，前面的是后面的前提。

#### 1. 不是 Git 仓库也能打开

现状：`FolmiModel+ProjectRecovery.swift` 遇到没有 `.git` 的文件夹直接报「不是 Git 仓库」。

- 打开普通文件夹时问一句：「Folmi 会在这个文件夹里记录版本，用来撤回 AI 的改动。不会上传到任何地方。」同意后在后台 `git init` 并存第一个版本。
- 不想在用户目录里多一个 `.git` 的（比如文件夹本身在 iCloud / 同步盘里，或已被别的工具管理）：用独立的 `GIT_DIR` 放在 Folmi 自己的数据目录，`--work-tree` 指向文件夹。和原则 1 不冲突：状态仍然全在 Git 里，只是用户看不见。
- 要想清楚：同步盘里的 `.git` 会被同步冲突弄坏；Obsidian 库里的 `.obsidian/` 默认写进排除列表；大附件（图片、PDF）默认不进版本还是进，需要日用后定。

#### 2. 修订视图里按段落收下

现状：`MarkdownDiffPage` 已经能渲染出新版、标出新增和修改的块、把旧文字划掉放在上方；但收下、丢弃走的是差异画布的按块 / 按行暂存，和渲染视图是两套。

- 在渲染差异里，每个改动块旁边直接给「收下 / 退回」，快捷键同逐个验收。
- 「一处」按 Markdown 块定：段落、列表项、表格行、代码块、标题。底层仍是按行暂存：把一个块对应的行范围（`marks` 里已经有）转成按行暂存，不另记状态。
- 段内只改了几个字时，在段内做字词级高亮，不要整段标红。中文按字、英文按词。
- 跨文件的「全部改动」也用渲染视图，按文件分节，顶上写「12 篇 · 47 处 · 还没看 31 处」。

#### 3. 文档模式（界面减法）

- 用词替换：提交 → 存一个版本；推送 / 拉取 → 同步（只有设置了远端才出现）；暂存区 / 工作区 → 收下的 / 还没看的；丢弃 → 退回。和 direction.md「下一步」里往「收下 / 没看的」靠是同一件事，可以一起做。
- 默认藏起来：分支、stash、提交图、终端、冲突处理的三栏界面（真遇到时再出现，并用一句话说清楚发生了什么）。
- 历史改叫「版本」：按时间列，点开是渲染后的整篇和与上一版的修订对比；能把某一篇或某一段退回到这个版本（结果放进还没看的，不直接收下）。`DocHistory.swift` 已有单篇的渲染历史，往这个方向扩。
- 是否单独做模式，还是项目级开关自动判断（仓库里 Markdown 占绝大多数就默认文档模式）：待定，倾向手动开关加首次打开时建议一次。

#### 4. 文档特有的检查（提交前检查的文档版）

AI 改文档常见的坏法，存版本前提示，不拦：

- 链接断了：改了标题导致锚点失效、改了文件名导致 `[[双链]]` 或相对链接失效。`MarkdownLinks.swift` 已有链接解析。
- 图片引用指向不存在的文件。
- front matter 被改坏（YAML 解析失败），或标签、日期字段被动了。
- 大段内容被删（某篇少了 30% 以上），提示「这一篇删了很多，确认是想要的吗」。
- 术语不一致：项目里定过的术语表（可由「越用越顺手」的规则来），AI 换了说法时标出来。

#### 5. 接 AI

- 有 Claude Code / Codex 钩子的照旧按轮次接入。
- 没有钩子的（桌面 agent、别的编辑器里的 AI）：监听文件夹变化，按「安静了 N 秒」切成一批，当作一轮。
- 退回时可以附一句原因，像现在的评论一样送回 agent；反复退回的归纳成规则写进 CLAUDE.md / AGENTS.md。对写作者来说这就是「AI 渐渐学会我的文风」，是最强的留存点。

### 不做

- 所见即所得编辑：和 direction.md 一致，以阅读为主。
- 多人协作、评论共享、云同步：这是 Google Docs / Notion 的领域；Folmi 只管本机的「AI 改了什么」。
- docx / PDF 修订：不碰二进制文档格式。要做也是「导出修订记录」，不是读写 docx。
- 自带 AI 写作助手：仍然不重造 agent。

### 先验证什么

在动手前，用现有 App 加最小改动验证三个假设：

1. **他们真的让 AI 一次改很多文件。** 找 3–5 个在用 Claude 改 Markdown 的非开发者，看他们最近一周的用法。如果多数只改单篇、单段，Folmi 的「批量验收」价值就小，Word 修订就够了。
2. **渲染视图里按段收下是他们要的那个动作。** 先只做第 2 步里的段落收下（开发者用 Markdown 时也受益，不浪费），给他们一个已经 `git init` 好的文件夹试。
3. **藏掉 Git 后不会在某处卡死。** 观察第一次遇到同步冲突、文件被外部改了、AI 改到一半中断时会发生什么。

假设 1 不成立就停；成立再做 1（隐式仓库）和 3（文档模式）。

### 衡量

- 每轮改动里逐处看过的比例（而不是闭眼全收）。
- 退回后用撤销找回的次数：太多说明「一处」切得不对。
- 留存：一周后还在用的人数。收工卡片已有每天验收数量和连续天数，可以直接用。
